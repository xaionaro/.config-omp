# Testing Discipline

- [Prod-code focus](../../eci-binding-contract.md#prod-code-focus) governs: tests are means to prove prod behavior, never a gate or goal. These rules govern the tests and checks you choose to write or run.
- Prove every modification with the shortest faithful evidence before reporting its Job or outcome done, not at each work-tree leaf close: use an automated check, a direct run, or both, whichever supplies the shortest faithful proof. Within ECI, E2E cadence follows its router. Unit isolates; E2E proves user path.
- E2E = built artifact in target env, exercised through the real UI/API/CLI by a harness or by hand, validated by output/screenshots/state. Anything less is not E2E; name it honestly.
- Iterate on the shortest faithful check first. If behavior reproduces without full E2E (unit/API/CLI/component), debug there; use E2E for final user-path proof.
- Treat tests as falsification attempts — they try to disprove your code works. Cover edge cases, not just the happy path.
- **Assert behavior once**: Assert each behavior once per test level, as its callers or users observe it; program output is behavior. Never assert source text, prose wording, or implementation details: a behavior-preserving rewrite must keep tests green. For instruction files (skills, prompts, docs), assert only structure: links and anchors resolve, imports exist, routing tables link the intended modules, and names they share with a program (schema fields, flags, paths) match that program.
- **Prune on touch**: When editing tests, check each test of the behavior you are changing or testing; delete it if it cannot fail, restates the implementation (wiring, echoed inputs), pins incidental defaults, or repeats another test's assertion at the same test level.
- **Dual-sided testing**: Every test must confirm both that good behavior IS happening AND that bad behavior is NOT happening. Testing only one side leaves the other unverified.
- **Test validation**: Watch each new test fail without its code, then pass with it; a test that passes regardless of code correctness proves nothing. Run the failing case outside the shared tree, in a scratch export of the base commit, the last commit without the tested code: create a new empty directory `<dir>`, run `git archive <base> | tar -x -C <dir>`, then copy the new tests in. Supply ignored dependencies the export lacks, such as `node_modules`, by symlinking them from the shared tree or installing them. Where the export still passes them or does not build with them, break or stub the tested code in the export. Never stash, reset, revert, or break code in a shared tree for this. Break it once by hand; never commit loops that mutate inputs only to re-prove the test's own checks.
- **Discriminating proof on every bug fix**: Show evidence that exhibits the bug before the fix and its absence after: a test checked by the Test validation method, or a direct before/after run. "Passes after my fix" alone is worthless. Show both outputs in the report. Skip only when the change is a literal text edit a human can verify by reading the diff.
- Infeasible tests → document why + provide alternative verification.
- Use provided logs/stacktraces as verification evidence. Add logging if insufficient.
- Write deterministic tests only — real-clock dependencies cause flaky CI and non-reproducible failures.
- **Efficient tests**: Spend only the time and resources the assertions need; avoid repeated builds or setup, a process fork per line or pattern, and quadratic string scans. A suite run over 60 s is a test-upkeep issue: when cheap, profile where its time goes and remove avoidable costs; otherwise report it as a follow-up. It never holds delivery. Treat slowness in prod code as a product defect only when it regresses or misses a requested behavior or performance goal; fix it in that code, never by trimming or speeding up its test. Route prod performance defects under applicable product and coding requirements, not as test upkeep.
- **Speed-review record**: When you do a speed review: Skip the speed review while `test-speed-reviews.tsv` beside the suite's entry point has a row for the same command from a comparable host, unless the current run takes over 25% longer than the latest of those rows with comparable load. Append a row only when a review leaves the suite over 60 s with every remaining cost unavoidable, or at 60 s or less when the file already has a row for that command from a comparable host; create the file with the tab-separated header `reviewed_utc command revision environment elapsed_s remaining_costs`. `environment` names the host, OS/arch, tool versions, and load average at start and end; `remaining_costs` names each remaining cost and why it is unavoidable, or holds `-` in a row at 60 s or less. The record never holds delivery.
- Add useful test cases where automation pays; coverage is a signal, never a target or gate.
- Language test conventions (preferences, at most `NIT`, never acceptance gates): Go: `github.com/stretchr/testify`, `assert` for soft and `require` for fatal; start each test function with `t.Parallel()` unless it changes process-wide state: environment, working directory, or any package's variables, such as `time.Local`. Python: `pytest` as runner with direct `assert` statements, not `self.assertEqual`; fixtures for setup/teardown; parametrize for variant coverage.
