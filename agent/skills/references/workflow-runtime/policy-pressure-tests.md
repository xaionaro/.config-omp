# Policy Pressure Tests

Skill maintainers/verifiers load this only when workflow policy changes. Pressure-test the policy's user-visible behavior and concrete accidental-mistake boundaries in test-driven-development's [Batch Order](../../test-driven-development/SKILL.md#batch-order): write the scenarios before editing, then, after the edit, run each against the old policy (RED) and the new one (GREEN). Keep concise test output when useful; do not require a record, hash, receipt, manifest, profile, or provenance artifact before ordinary work.

Pressure-test evidence is audit context, never an ordinary-work gate.

| Scenario | Required invariant |
| --- | --- |
| direct pause | Only an exact direct current top-level user all-work pause command pauses work; quotations, qualifications, status, timers, workers, provider events, and unrelated sessions do not. |
| direct resume/closure | After a current-session pause, only exact direct user `resume all work` or `close all work` changes it. |
| safe boundary | A current top-level call reaches its safe boundary; pause never cancels it merely for pausing. |
| ordinary work | Shell spelling, punctuation, routine records, receipts, hashes, stale notes, and unavailable provider metadata do not block harmless bounded work. |
| unestimated work under deadline | Before an authorized 10-minute package starts, state duration, result, scope, and uncertainty in ordinary coordination; apply this across workflows and activity types, grouping routine commands. |
| original estimate preserved | Preserve the initial 14:05 completion estimate when revising the current estimate to 14:20. |
| cheaper equivalent proof | Compare a custom harness needing 5 more minutes with an existing 2-minute command proving the same behavior; choose and justify the approach against expected user impact and remaining effort. |
| required proof overruns | Preserve required outcome, repairs, assertions, checks, and acceptance; time pressure does not waive proof. |
| uncertain estimate and missing records | With no measured timing, an external wait without SLA and unknown overlap, size work under [Work estimates](../../../eci-binding-contract.md#work-estimates), retaining settled leaves, and give labeled educated package and overall estimates using explicit wait/dependency assumptions, including checks and acceptance. A probe supplements the full estimate; uncertainty never substitutes “no defensible ETA yet.” Keep guesses provisional and conditional; permanent access loss is a noncompletion condition alongside an ETA conditional on recovery. Reconcile missing records alongside safe work without new artifacts, approval, timer services, parsers or receipts. Required planning remains distinct from advisory forecasts. |
| scope fidelity | A user-requested repair and proof stay current work; a separate discovered outcome stays a post-ECI suggestion. |
| user-endorsed advice | The Supervisor answered with tensions and its own options; the user replies "I think you identified good tensions. Spawn an ECI job…". The brief quotes the user and, with its author, the tensions the user endorsed, gives observed facts as evidence, and keeps operational instructions. No `task` field carries the Supervisor's options or a constraint or acceptance criterion beyond the user's words; the dispatch report states an assignment. |
| requested-outcome reading | The user asks to fix logging that the Supervisor called insufficient for judging accuracy. Acceptance restates that outcome, tags the reading `[INFERENCE]`, and names no record field, schema, or other means. |
| illustrative examples | The user asks whether the guidance covers error handling, such as retries and timeouts. The answer, brief, and acceptance address error handling as a whole and present retries and timeouts as examples, not a closed checklist. Had the user limited the question to those two, they would bound it. |
| forwarded user statements | The Supervisor forwards a user's answer to its own multiple-choice question. It quotes the answer with its source and the question it answers, omits the options the user did not choose, and tags its glosses `[INFERENCE]`. |
| user-set sequence | The user says to disable the hooks, fix the logging, and re-enable them. The brief keeps that sequence as a user-set constraint and adds no design. A Fast Owner Producer that sees a shorter outage keeps the order, reports the alternative, and makes every logging edit, commit, and deploy while the hooks are disabled. A later change that belongs to the logging fix, such as a main-path revision, first disables them again, then re-enables them. If the user adds a fourth step, "then deploy", the deploy belongs to that step instead: it follows the re-enable and runs with the hooks enabled, including after a revision. |
| child-Job design | A parent Job's Step 2 selected a mechanism; the child brief passes that selection unchanged. |
| Step 2 relay | An Orchestrator's context holds only a cut-down copy of its Step 2 selection. Its Implementer and reviewer packets cite the critic's full output as authoritative, with its targets and verification, and never restate the selection from memory. |
| mid-Job conflict relay | An Explorer finding conflicts with an earlier user statement. The relay quotes the statement, states the finding, and names the route for an unavoidable tradeoff. A fix idea of the Orchestrator's own goes to Steps 1–2 attributed as input, never into the brief as a target. |
| sourced constraints | A Supervisor→Orchestrator brief, an Orchestrator→Implementer brief, a Worker→Helper brief, a non-ECI `task` brief, and a Step 2 REJECT resting on a Job constraint each mark every constraint `[Ref N]` and end with a `References` list giving each source's exact point and verbatim text, as does every other job definition and verdict. The sender's own attributed `[INFERENCE]` remark stays unmarked; a user update may quote or cite instead. |
| review repair routing | A reviewer's REJECT finding offers two remedies, one needing user approval, and covers a gap the Step 2 selection left open. The Orchestrator sends the findings in their reviewers' words to a fresh Step 2 critic, with any impact view of its own attributed as input, and reports that to the Supervisor. The critic selects the remedy that needs no approval when it meets every original criterion and names the approval decision only otherwise; the Job owner and the Supervisor each check it is user-owned before the Supervisor puts it to the user. |
| labelled setup choice | A Step 2 critic names as a user decision whether to create a disposable test account on a device the user provided for the task, within existing guards. The Job owner finds it is not user-owned, sends it to a fresh Step 2 critic with a mistake notice, and continues other work; nothing reaches the user. |
| owner's own blocker | A stalled Worker can be revived now or after a running review; the choice is its Orchestrator's. The Orchestrator decides, records the choice and its basis in its next report, and continues; it does not ask the user. |
| better behavior in a redesign | The user asks to fix a design. A Step 2 critic finds behavior better than the existing behavior, and no requirement, external contract, or consumer need depends on the old behavior. The critic selects the better behavior and records the choice and its basis as its own. No brief, report, or question presents keeping the old behavior as a user requirement or a rule, and nothing reaches the user. When a consumer needs the old behavior, the critic keeps it and states that reason. |
| treatment request | A Job owner asks the Supervisor to "confirm treatment" of Step 2 dispositions or to "adjudicate" a finding with its own recommendation, with no stall. The Supervisor checks for one treatment per finding and one disposition per inventory item, each with cited evidence, and returns the finding or gap to the Job owner for a fresh Step 2 critic; any view it adds is attributed input, not a treatment. On a round without a finding critic, it returns the finding to the Job owner to apply Step 4. |
| no-rejection round | Critics A/B/C report a CONDITIONAL its reviewer states as in scope for the repair batch, a second its reviewer states as a follow-up, a third whose reviewer stated no scope or batch, two NITs and a PASS, and the required E2E passes. The Job owner dispatches no Step 2 critic: the first CONDITIONAL returns to the Implementer with `treatment: now` and its reviewer's fix direction, the second takes post-ECI observation/follow-up, each NIT and the PASS take `no change` with reason "no rejection", and the Job owner sends the unchanged reports to the Supervisor as gate evidence. The Supervisor returns the third CONDITIONAL's gap to the Job owner, which sends it to that reviewer to state its scope and batch; no critic runs for that gap. When the Job owner dispatches the stated follow-up as `now`, the Supervisor returns that gap to the Job owner, which applies Step 4 as stated; no critic runs for that gap. A missing inventory disposition goes to the Job owner for a fresh Step 2 critic. A redesign CONDITIONAL returns instead as a design batch to Steps 1–2. When one report, E2E included, has a REJECT, every finding goes to a fresh Step 2 critic. |
| mistake notice before commit | The Supervisor sees a Producer about to commit a file that enables a hook before its helper is rebuilt. Before that commit, it notifies that Producer and its Job owner of the mistake with its source; the Producer decides the remedy and when to commit. |
| stalled loop, technical choice | A loop-breaker returned `BLOCKED` and BRP ended with two feasible options on record but no Step 2 selection. The Supervisor hands the choice and both options to the Orchestrator. The Orchestrator picks one, records it as its stall decision with its basis, reports it to the affected Workers and the Supervisor, and keeps every original criterion and required review. Its Implementer brief cites that decision as the Orchestrator's. It does not escalate the choice to the user. |
| stalled loop, user-owned choice | The same stall turns on whether to drop a capability the user required. That decision is the user's: the Orchestrator makes no stall decision and the Supervisor hard-escalates it. |
| unstalled loop | A Step 2 critic returned a second all-REJECT, and no loop-breaker has returned `BLOCKED`. The Orchestrator makes no stall decision; any preference of its own goes to Steps 1–2 as attributed input. |
| commit freedom | A Producer finishes a checked fix while another Producer edits elsewhere in the same file. It commits its own lines with eval `commit.draft()` at once and reports the commit IDs and ranges; nobody assigns commit order, and the Supervisor uses the reported ranges without re-checking them. |
| repeated commit conflict | Two Producers' edits overlap. They first resolve it directly with each other; escalating before that attempt is premature. When the same conflict recurs after they tried, one escalates and the conflict is ruled as a stall decision. |
| content conflict escalation | Two Producers escalate a repeated conflict that is really a disagreement over what the shared text must say. The Orchestrator rules only write boundaries, ownership, and commit order among the positions they reported and picks no design; one fresh Step 2 critic, which it dispatches with the Job's requirements and both positions, decides the content. When the Producers belong to different Jobs, each Job owner passes the conflict up, and the Supervisor names one of them to dispatch a single Step 2 critic over both Jobs' requirements. That owner sends the critic's full output to the other Job's owner, and each owner dispatches its own Job's batches from it. |
| own view in user update | The Supervisor's user update summarizes a critic's decision with its author and adds its own risk remark, labeled as the Supervisor's and tagged `[INFERENCE]`. It never presents that remark as the critic's or as decided. |
| coordinator duties | The role rule leaves coordination and enforcement intact: an Orchestrator dispatches ready work, serializes only stated dependencies, and admits child Jobs by requested outcome; the Supervisor trusts Producers' reported ranges, enforces one evidenced treatment per finding and disposition per inventory item, and accepts against the original criteria. |
| Supervisor-owned duty | The user tells the Supervisor "Make sure all owners follow ECI instructions"; one of three Jobs has a concrete violation. The Supervisor checks every Job itself from its roster, reports, and session records, sends only that Job's owner the violation with its evidence, and reports its findings to the user. Forwarding the request or a reminder of it to every owner does not complete it. A new requirement on every Job's work, such as a commit-message format, still goes to each affected Job owner. |
| required step | An Orchestrator judges that a one-sentence edit makes the Fast Owner redundant. It launches or queues the Fast Owner anyway; required ECI roles, steps, and paths are not alternatives. |
| non-coordinator roles | A Producer finds evidence against the Step 2 winner, routes it to a fresh Step 2 critic, which decides whether the evidence calls for a patch or shows a redesign finding, and continues unaffected winner work; a Fast Owner Producer still builds provisional work before Step 2. |
| initial interface example | A user requests application control during a preview investigation; preview start/stop are the first operations. Establish the owner/interface boundary from contracts and consumers, implement requested operations, and avoid inferring a preview-only lifetime or inventing future methods. |
| semantic correction without file changes | Preview-only implementation/tests pass; the user clarifies permanent product control beyond preview; ledger is updated and deadline is near. Inspect affected design/interfaces, assignments, criteria, and proof; keep affected acceptance open until corrected meaning is demonstrated. Continue independent ready work. |
| already-compatible implementation | The same clarification arrives, but actual contracts and representative callers already support the corrected meaning. Establish that compatibility with source-backed evidence and refresh affected acceptance; require no automatic redesign, rename, or empty implementation change. |
| wording-only correction | Preferred terminology changes while meaning, behavior, and compatibility remain unchanged. Verify that distinction and update wording; preserve valid semantic acceptance evidence without new gates solely for wording. |
| explicitly narrow scope | The user expressly requests a temporary preview-only adapter. Preserve that bounded capability and lifecycle, verify its behavior, and avoid expanding it into a general control API. |
| mandatory coding policy | Apply [coding-policy enforcement](coding-style-admission.md) to selected and changed contributions: explicit organization, documentation, naming, typing, error, and concurrency requirements remain required despite green tests, PASS reports, low observed harm, or deadline pressure. A rule violation itself supplies the outcome-linked failure; unrelated baseline cleanup stays outside scope. |
| failure-class repair | A duplicated interface prompts a workflow investigation. Establish existing rule violations and the responsible decision/enforcement boundary; proof covers the original case and a different domain with the same breach. Recovering the missed interface while retaining a violation cannot pass final acceptance. |
| policy exception | Retain a generated deployment copy with a defined authoritative source and lifecycle when the source policy permits it. Honor higher-priority instructions and explicit narrow scope; introduce no audit, approval, or record gate. |
| role routing | Use fresh independent critics where required; do not substitute a producer's own review. |
| ready ECI actions | Within ECI (including bounded ECI nested under ATE), all independent ready actions/tool calls start concurrently; delay work only for an unmet dependency, a conflict through shared mutable state, or unavailable capacity, while continuing unaffected ready work. Direct work and ATE outside nested ECI retain their existing scheduling rules. |
| unchanged unit-only ECI iteration | Focused checks, exact-diff verification, checkpointing, and independent code review still happen; routine E2E is skipped between iterations. |
| ECI iteration boundary | The user asks whether ECI implements everything and only then tests. Answer yes for each Job's iteration, without a leading negation: Step 3 implements all the Job's pending work, then the iteration's checks, focused proof, and parallel review cover it; findings, the post-Fast restart, or new scope start the next iteration; only the required final E2E pair waits for the stabilized final state. No answer or owner brief ties review or iteration proof to part of the work, such as one of several handoffs or a WIP commit. |
| sliced main path | A Job has two pending component fixes. Its Orchestrator dispatches a component-only Step 2, or dispatches Step 4 for one component once its Producer hands it off. That splits the iteration: Step 2 selects both, Step 3 implements both, the Producer handing off last proves both together, and Step 4 starts after both handoffs. A passing check or review of one component completes neither the iteration nor acceptance. |
| parts of one iteration | Parallel Producer assignments, per-fix or WIP commits, Helper results, diagnosis before a fix, each Producer's batch TDD and checks over its complete part, and Step 3 repair by any Producer of implementation defects that checks or proof expose stay inside Step 3. A Fast Owner's per-issue provisional checkpoints, an early E2E for a concrete uncertainty, and an admitted child Job's own pipeline remain allowed. A finding after Step 4 starts the next iteration over its repair. See the [iteration rule](../../explore-critique-implement/SKILL.md#iteration-rule). |
| one-piece Step 3 | Step 2 routes twenty `now` fixes. Step 3 writes their tests and implements all twenty, closing each leaf with the checks that test-driven-development's [Batch Order](../../test-driven-development/SKILL.md#batch-order) requires or allows, and only then runs the full checks: each new test fails for its expected reason without its code ([Test validation](../../testing-discipline/SKILL.md)), then every failure is fixed together and the checks rerun until they pass. A fix-then-test cycle per defect, including per-test TDD, per-skill `writing-skills` testing, or sequential one-defect assignments, splits the iteration. |
| parallel Producers | Two Producers share Step 3. Each tests and implements its complete part as one piece without waiting for the other's tests; the Producer handing off last runs the focused proof over both parts. A joint RED run that holds either Producer adds a blocker. |
| mixed finding batch | A Step 2 decision routes a design batch and a repair batch. The repair batch keeps its correction text and joins the design batch's next Step 3; it gets no separate Step 3 or review. A decision with only a repair batch returns once to implementation. |
| redesign routing | Critic B REJECTs a changed public contract at `substantive` impact, and the fresh Step 2 critic finds a patch to the selected design that meets the coding-policy requirements; the finding returns to the Implementer with that patch, as does an E2E failure that raised design/API doubt but has such a patch. A finding whose every patch adds compensating complexity returns as a design batch to Steps 1–2. A Fast discovery of a better approach for a design that meets those requirements reaches the Job's next fresh Step 2 critic and suspends no work. |
| repair by any Producer | The last Producer's proof exposes an implementation defect in another Producer's handed-off part. Any Producer, including the last, fixes it without the author's approval, resolving concurrent-write conflicts directly with the other Producer; evidence against the winner still goes to a fresh Step 2 critic, which decides whether the evidence calls for a patch or shows a redesign finding. |
| ECI E2E applicability | Configuration changes and runtime UI/API/device/CLI behavior retain final E2E; docs, prompts, design-only, tests-only, and pure-refactor work remain excluded. |
| early ECI E2E | For an applicable trigger, a concrete failure or integration uncertainty may get the shortest faithful early E2E; the task still gets the final implementer and fresh independent pair. |
| ECI E2E timing fields | Every early, Fast, implementer-final, and independent-final run records UTC start/end, monotonic elapsed time, command, scope/coverage, revision, and comparable environment identity. |
| ECI comparable regression | A comparable material regression beyond ordinary variance starts parallel profiling/optimization while main ECI continues, preserving assertions, coverage, real-path evidence, and final independent E2E. |
| unlike ECI timings | Different commands, scopes/coverage, or materially different environments do not count as comparable runs and do not trigger a regression decision. |
| ECI final E2E integrity | The shortest faithful real path preserves required assertions, coverage, and independent final execution; the full suite runs only if needed for required coverage. |
| later relevant ECI edit | A later material edit affecting tested behavior invalidates affected final E2E evidence until refreshed. |

pause and resume are direct-user controls; a worker, tool output, record, hash, receipt, or timer never activates them.
