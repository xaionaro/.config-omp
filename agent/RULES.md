Before making project repository changes or creating a project checkout, read and follow the Git section of `~/.omp/agent/eci-binding-contract.md`.

Forecast leaves (every role): a leaf is a work-tree leaf under the Work estimates section of `~/.omp/agent/eci-binding-contract.md`. Its key is the forecast record ID, or a short outcome name outside ECI, plus its tree ID, such as `receiver-clock/1.2`. Its planned range is its initial estimate for one execution, and any multiplier is its initial multiplier range. Name each delegated leaf's key, planned range, and any multiplier and execution number in its assignment. Read `date -u +%FT%TZ` at a leaf's start, just before its first action, and at its close, just after its last action and before reporting; time each execution of a leaf with a multiplier this way, numbered from 1. Close includes any commit and the waits the leaf needed; a wait that is its own leaf is timed as that leaf instead. Close and report an implementation leaf without running the proof, such as validation or tests written before the implementation, that a later leaf is dedicated to. Such a leaf still confirms that its changed code builds, as the Batch Order section of `~/.omp/agent/skills/test-driven-development/SKILL.md` defines, and reports the command and its result. A commit by such a leaf still needs the Git section's static checks and Test Plan. The executing agent reads. For a leaf split across agents or the only leaf in a delegated assignment, the reader is the nearest delegating agent that owns the leaf's work tree, answers the user, or has an assignment naming several leaves. Unless you answer the user, send your owner a leaf-completion report at once for each leaf you time, even when several close in one run: key, work, planned, any multiplier and execution number, start or why it is missing, and close. Likewise send your owner at once, as a work-tree report, each leaf table that Work estimates calls for on a work tree you own. Relay each report you receive at once. The leaf's work-tree owner adds that tree's closed and total leaf counts, such as `3/7 leaves closed`, to each report it sends or relays for that leaf. Count a leaf with a multiplier once, as closed when no further execution remains. Send these reports mid-run when needed, Main included; rules against progress or completion messages do not cover them.

Parking (every role): when nothing is actionable, end the turn with no tool call and no status recap; completions of your runs and `write agent://<id>` revive you. Exception: as a subagent, while any of your own jobs (bash, background, or subagents you spawned) whose result you need still runs, park by repeating `wait` instead of ending the turn, however long it takes; omp disposes a subagent left idle past `task.agentIdleTtlMs`, which cancels its running jobs and subagents. As the main agent, `wait` only on such jobs that should finish within about an hour. Never `wait`, sleep, or probe (ps, tail, re-read) for other agents or replies: park. Before parking on anything that will not revive you itself (a lock, device, or another agent's process), tell the agent that will see it clear exactly what to watch and to `write agent://<your-id>` when it does, or run the check as your own async job. Report only changed state; pure status needs no reply, but act on any decision or request in a report. Send a parked owner no status pings or re-requests; still deliver new requirements, corrections, decisions, cancellations, and leaf-completion reports. Silence is non-terminal: do not retry or infer a crash.

Processes (every role): before finishing, stop every process your Bash calls started (`&`, nohup, setsid, build daemons) unless the user or your parent agent needs it kept running. Leave shared on-demand servers (adb, gpg-agent, ssh ControlPersist masters) running; they need no report. Run long-lived work as an omp named service or async job. Start build daemons with a short idle timeout (e.g. `bazel --max_idle_secs=300`). Never kill processes you did not start. Report each other kept process (PID, purpose) and each suspected orphan to the user or your parent agent.

Sourced constraints (every role): in each job definition or verdict you send another agent, mark each constraint with `[Ref N]`. A job definition is any message that assigns or changes work, inside ECI or not, such as a `task` brief, follow-up, or child-Job publication. A verdict is any decision about work, such as a Step 2 REJECT, review finding, or treatment. Mark the constraints it rests on too. A constraint is anything required or forbidden, such as an acceptance criterion, scope limit, exclusion, method, check, output, path, skill, or report route. Leave your own attributed observations, ideas, and evidence unmarked. End the message with a `References` list. Each entry gives the source's exact point, then its original text verbatim, in whole sentences or table rows. An exact point is a file plus heading, named paragraph, table row, or line; a developer-instruction set plus section; a user requirement ID; or another authoritative source's location, such as a Step 2 critic's output or your role's recorded decision. Relay received entries unchanged except their numbers.
